# EM 执行链路：取数、入库、执行与收束

EM 每轮按本页执行。角色边界见 [EM.md](../roles/EM.md)，字段归属见 [多维表格契约](bitable-contract.md)。日程、配额、硬筛条件、排除词、超时时长等具体数值只读私有 `settings.json`，本页不给默认值；缺就停在相关步骤，回到 [Initial Setup](first-use.md)。

EM 不做任何生成工作：不排岗位先后，不给批准或拒绝建议，不写招呼语、简历、匹配档位或批准状态。

入库与进度更新使用注册 Bot。该类写入按 [本人 Trace 契约](human-signal-capture.md) 过滤，不触发 Human Signals。

## 1. 平台与执行方式

先读 [招聘平台能力路由](platform-capability-routing.md)。BOSS、猎聘、智联、LinkedIn、企业招聘官网 / ATS 和小红书都按本人选择和当前宿主实测状态运行。Chrome 插件、云浏览器、MCP 等入口由 Setup 探测，按授权、验收和任务模式决定。

使用 `jobagent setup platform-routes` 获取对应平台本轮入口。定时运行需要后台能力验收、本人定时授权与确认过的业务配置。平台未就绪时记下原因并继续其他平台。说明本次实际使用的入口。遇到平台限制时停该平台。

## 2. 每轮开始

1. 读私有设置与当前路由，核对平台、已验证入口、每站与合计配额、硬筛条件和排除词。缺业务条件时继续其他就绪平台。
2. 看 `Muse处理`：不为空就处理 GM 的回复与搜索策略要点，处理后修订该列。
3. 读当前的搜索与匹配记忆，记下版本，本轮沿用该版本。GUI 以平台推荐、搜索与岗位详情为候选来源，用 Memory 重排序与辅助入库。MCP/CLI 按本人方向、硬筛和 Memory 生成检索词，再匹配与重排序。只有本人确认的规则可作硬筛。临时负面信号只影响对应情境。

## 3. 取数与入库

1. 按平台与方式检索，不为凑配额放宽硬筛。
2. **详情链接用平台返回的原始链接**（可去掉明显的跟踪参数），不手拼 URL。
3. 去重：先对当前岗位表，再对本人保留的历史备份或终态记录；按岗位 ID 或会话，不按公司。已联系、已拒绝、已终止、已废弃的记录不复活；本人要求再联系时新建一行，并在岗位 ID 后加 `_R2`、`_R3` 区分。
4. 逐岗读完整 JD，再按私有设置的硬筛顺序判断。薪资口径不一致、缺薪资或无法判断的，交本人，不自己猜。
5. 入库：写岗位名、公司、薪资原文、原岗位链接、JD 全文、招聘平台、岗位 ID，`处理进度` 写初次入库；写后读回，确认附件在位、`批准状态` 未被动过。
6. 如实区分完整读取、部分读取、登录失效、未加载与受限；读不到不算“没有岗位”。JD 全文只存表里或本人私有区，不贴进聊天或交付文档。

## 4. 执行已批准的动作

- 仅在本人在飞书表格将该岗位的最新 `批准状态` 设为 `已批准` 时，才通过已授权、已验收的执行入口，使用表里当前的 `招呼语` 和有效 `简历cv（PDF）` 执行相应动作。收到对话请求时重新读取表内状态。
- 发送前重新打开原岗位链接，核对岗位仍在、JD 与入库时一致；会话里已经有本人发过的消息就不再发。
- 招呼语原文一次性发送，不改写、不截断。平台有真实字数限制时停下，把原因写进 `GPT处理` 交给 GM。
- 发送后把 `处理进度` 改为首次沟通，写回并读回。结果不明时先去平台核实，**不重复发送**。

## 5. 回执核对

每轮读消息中心时核对已联系岗位的回执与简历事件，按平台页面上亲眼看到的最晚状态更新 `处理进度`：

- 看到“已读”才改为对方已读；“首次沟通”只说明会话存在，不等于已发出招呼语。
- 对方索取简历改为对方要简历；系统提示简历已发送改为简历已投。
- 招聘方明确拒绝时，只有本人事先授权过，EM 才能直接改为已终止；否则写进 `GPT处理`。
- 招聘方来信需要回复时，EM 在 `GPT处理` 里写“招聘方来信，待 GPT 回复：”加来信的原文要点，由 GM 起草回复、写回表里等本人批准；EM 不起草、不自己回。
- 记录只覆盖 EM 经手的动作。本人在 App 里自己点的操作不在记录里，不能凭记录断言某事没发生。

## 6. 状态收束

`处理进度` 的取值以本人 Base 的选项为准，常见顺序是：初次入库 → 招呼语（初稿）→ 首次沟通 → 对方已读 → 对方交互中 → 对方要简历 → 简历已投 → 面试已约；任一阶段都可能进入已终止或已废弃。

本人设置了超时规则时，每轮取数结束按私有设置检查。时长、按工作日还是自然日、生效时间都只读私有设置；目标状态以本人的设置为准，本人当前的约定是 `已终止`。

**时钟用状态的业务时间，不用整行的 `更新时间`。** 用 `jobagent feishu record-history` 读该行的原生修改历史，取最近一次 `处理进度` 改变的时间；该行入库后 `处理进度` 从没变过，就取历史里 `create` 那一条的时间（即入库时间）。所以交接留言、`进展` 备注、Dream 或补证的写入都**不重置**时钟。历史没读完、读不到或缺这两条时，该行这一轮不自动收束，列给本人核对；不拿 `更新时间` 顶替，也不猜入库时间。

满足下面任一情形的行暂停计时，不自动收束：

- `批准状态` 是 `待你批准`，或 GM 还没评级：等的是本人或 GM，不是招聘方；
- 已批准但发送前复核发现 JD 已变而停发，正等本人决定；
- 有招聘方来信还没回复，或来信后 `处理进度` 还没跟上（先对账，不算未触达）；
- 该平台本轮登录失效、页面不可观测或受限，回执核对没做完；
- 已经是终态。

超时的行改为 `已终止`，并在 `进展` 或 Memo 注明“已超时”、所用时钟（哪一次状态变化或入库）与工作日数。同一个 `已终止` 也用于招聘方明确拒绝，所以“已超时”注记必须写，10 日谈靠它和历史里的操作者区分两者。超时只说明流程到期，**不证明**招聘方已读不回。

每次改 `处理进度`，同时在进展或 Memo 写明原值、新值、依据与时间，并读回确认 `批准状态` 未被动过。

## 6A. 超时后补证

每次真实发生的超时收束，派生**一次**定向补证，`origin=system_timeout`。

1. **先看**有没有已经存在的同一任务：任务键是 `CH10D-<岗位ID>-timeout-<收束日期>`。先看 `Muse处理` 与 `GPT处理` 两列：已经有这个键（包括本人或 GM 早先写下的 `CH10D-` 委托）就接着处理或直接消费结果，不再写第二份。
2. 只查表里证明不了的事：招聘方最近活跃的原始标签、岗位是否还在招、真实的发送 / 已读 / 回复 / 索取简历 / 约面、本平台最近一次**完整**巡检的时间。不重抓 JD、薪资、档位或招呼语。
3. 页面只显示“近期活跃”就照抄原标签，不补造时间；平台本来就没有已读标记记 `unobservable`；没看到不等于没有，看不到记 `unknown`。
4. 结果按下面的格式**追加**进该行 `GPT处理`，保留原有留言；写后读回。`进展` 可同步一行摘要。
5. 不改 `批准状态`、材料或 Memory；不因补证给招聘方发任何消息；补证发现对方其实已回复时，只写进 `GPT处理` 交 GM，不复活已终止的行。

```text
CH10D-<岗位ID>-timeout-<日期> | origin=system_timeout | status=completed|partial|blocked
hr_activity=<原始标签或 unknown> | listing=<在招|已关闭|unknown>
sent=<hit|unknown> read=<hit|miss|unobservable|unknown> reply=<hit|miss|unknown>
last_full_patrol=<时间或 unknown> | 来源=<平台页面 / 会话位置>
```

## 7. 每轮汇报

用四行向本人汇报，每个数字都有出处；未执行、失败、部分完成、核实为零分别写明：

- **完成**：实际执行的操作与结果；
- **未完成**：没做完的事和真实阻塞（查了什么、看到的报错或页面现状）；
- **需本人**：要本人决定或在平台上亲手完成的事；
- **恢复点**：下一轮从哪里接着做。

执行中发现的其他问题记为待办，说明对主链路的影响，不自动展开执行，也不捆绑到下一轮。

## 8. 停止

登录失效、验证码、风控、限流或页面与预期不符时，停下该平台，不绕过、不换账号、不重试；其他平台照常。阻塞只影响对应平台或步骤。不推断未打开会话的内容，不把模型整理过的文字当作页面原文回传。
