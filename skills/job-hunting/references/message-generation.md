# 消息生成策略

首条招呼统一采用完整 JD、材料表里的本人资料与适用的招呼语表达记忆生成全文并自查，不再调用历史挑句结构或首招字数硬上限。

默认写作方法是随包的 [jd-greeting v1.1.0](../greeting/SKILL.md)：GM 起草时按它的流程与参考执行。事实、批准与外发仍以本文件、[多维表格契约](bitable-contract.md) 与 CareerHarness 规则为准；它的输出 JSON 与状态只作参考。

投递消息(打招呼语、求职信、邮件正文)与简历受同一套事实规则约束。求职信是最容易出现编造的地方,因为它的文体鼓励概括与自我评价。

## 事实规则

- 消息中的每一条**实质性主张**都必须来自材料 md,与简历条目同标准。
- 允许出现的无出处内容仅限于:意向表达、对职位的兴趣、可安排的时间、礼节性措辞。这些不是主张。
- 禁止把简历里已收窄过的表述在消息里重新放大。

## 禁止项

- 不得凭空造出年限、规模、增长率、团队人数、营收数字。
- 不得把参与表述为主导,不得把协助表述为负责。
- 不得声称对该公司、该产品、该团队有实际了解,除非材料里写明了这种了解。
- 不得编造共同联系人、共同经历或推荐关系。
- 不得声称薪资预期、到岗时间、签证状态,除非材料 md 里写明了这些。

## 招聘方信息

- 只有当 EM 实际读到并写进岗位表的招聘方信息时,才使用招聘方姓名与职位。
- 招聘方信息缺失时使用中性称谓,不要猜测姓名、性别或职级。
- 不得把招聘方的个人信息写入日志、审计记录之外的任何位置。

## 语言与语气

- 消息语言跟随 JD 语言,除非招呼语表达记忆显式指定了其他语言。
- 语气默认为简洁、具体、事实导向。长度控制在能被完整阅读的范围内。
- 不使用夸张形容词("顶尖""完美契合""极其擅长")。用可核验的事实替代评价性措辞。

## 首条招呼

GM 按 [greeting-writing.md](greeting-writing.md) 阅读完整 JD、材料 md 和适用的表达记忆，重新生成一条完整消息，再自查。模型自行决定切入点、开头、背书、组织顺序与结尾，不读取旧话术库，不使用固定句子或固定结构，不在失败时退回模板。

1. **长度与表达**：简洁自然，围绕最相关的实际经历说明做过什么、服务谁及为何相关。仓库不设置首招字数硬上限；若平台有真实输入限制，宿主按已核实限制调整，不截断事实或替换已批准原文。
2. **事实与内容检查**：每项主张都来自材料 md，保留主体、职责、时间、范围和指标含义。不编造了解、称呼、背书或成果。仓库不内置任何人的禁用词或数字写法；这类写作偏好由 Dream 写进招呼语表达记忆。
3. **场景适用性**：行业资质、术语与经历按当前 JD 的实际相关性选择，不强制每条使用同一产品锚点、背书、开头或收尾。偏好仅影响表达与选材，不确认新事实。
4. **自查**：通读完整正文的事实来源、目标相关性和表达。事实不足或全文 JD 缺失时说明缺口，不产出假合格稿。
5. **一岗一条**：已联系过的职位不再起草首招，转后续跟进。
6. **匹配档位**：正常首招面向强匹配与可能匹配，弱匹配和不匹配只列缺口，不提升档位。未知结果保持未评估；本人提供岗位不自动提升匹配。偏好分只在现有准入和排序策略内生效。

## 与批准的关系

写完后把 `批准状态` 写为 `待你批准`。是否外发只由本人在 `批准状态` 决定；EM 执行前读取最新的招呼语。生成消息本身不构成投递意图。
