# 归因：先排查，再决定改什么

指标持续偏低只说明“有问题”，不说明是哪里的问题。旧版直接把回复率偏低判为招呼语问题、把约面偏低判为简历问题，这里不照搬。每一项都是待检验的假设，写清依据和其他可能的解释。

## 必须逐项排查的因素

| 因素 | 看什么 | 来源 |
|---|---|---|
| 岗位匹配 | `匹配档位` 构成是否变化；硬门槛、行业、年限、关键能力缺口 | `匹配档位`、`匹配理由`、`JD全文` |
| 薪资 | 区间是否可比、是否低于本人底线、计薪方式是否一致 | `薪资原文` |
| 招聘方活跃 | 岗位是否下线、刷新时间、招聘方最近活跃的原始标签 | EM 补证回执（`GPT处理`） |
| 投递时机 | 实际首次触达的日期与时段、岗位新鲜度、节假日 | 原生修改历史、`进展` |
| 平台差异 | 各平台的漏斗不能共用分母（有的先打招呼，有的直接投在线简历，有的没有已读标记） | `招聘平台` |
| 响应成熟期 | 是否还有大量 `pending`；完整巡检是否覆盖 | [指标](metrics.md) |
| 材料版本 | 招呼语版本、在线简历在**招聘方实际看到时**的版本、定向简历发出的版本 | 原生修改历史、`GPT处理` |
| 本人动作 | 本人主动终止或否决的比例是否变化 | `Human Signals` 与原生历史 |
| 测量质量 | `unknown`、`unobservable` 占比，巡检是否完整 | [指标](metrics.md) |

## 规则

- 对比改动前后时，按招聘方**实际看到的版本**分组，不按招呼发送日分组。跨过改动时间、又无法确定对方何时看到的样本单列 `crossover`，不归入任何一组。
- 观察期内如果同时改了别的东西（筛选条件、档位口径、平台配额），在结论里写明，不把效果全算给某一处改动。
- 能用表里已有的事实回答的，不再让 EM 去平台查；只有表里证明不了的，才写 CH10D 委托。
- 依据指不出一个可改的对象，就不写提案，只记观察。
- 结论分三段写：观察到什么（带数字和来源）、可能的原因（每条附依据）、其他可能的解释。推测不写成事实。
