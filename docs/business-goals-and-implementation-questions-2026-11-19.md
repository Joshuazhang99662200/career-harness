# CareerHarness：业务目标与实现程度对齐问题

日期：2026-11-19。状态：需求与现状核实中，尚未形成确认后的实现方案。

这份文档用于和业务负责人、现有 GPT/Muse 宿主及实现维护者核对事实。此前 Codex 对 Skill 职责、飞书权威和审批消费的理解曾出现偏差，对宿主正在运行的代码与任务也未完成核验。需要先回答这里的问题，再修订实施范围。本文不创建任务、不修改飞书、不执行招聘发送。

输入包括本人提供的 `CareerHarness_Codex_Implementation_Brief.md` 与本次对话。简报是设计输入，其中的能力判断与命令仍需核实；本人在对话中的后续澄清优先。文中的“待核实”不等于功能不存在。

## 一、已经明确的目标，不再重复询问

1. 架构保留 **Skill 的渐进式披露加载**。Skill 定义推理侧、执行侧与人通过飞书协同的完整链路，包含阶段职责、交接、事件、工具调用和结果要求。
2. 飞书多维表格是三方共同操作的共享业务环境，也是业务状态的唯一来源。Muse 等宿主内部不应另设一套能否决表内状态的业务账本。
3. `处理进度 × 批准状态` 联合定义当前阶段及获批动作，结合对应正文、附件和版本执行。不能拆开字段解释，也不能让本人重复回答已有 Schema 已定义的问题。
4. 本人在表内作出的真实批准应被消费；内部缺少一条批准记录不应导致重复审批或静默不执行。AI 不能代写本人的批准，材料变化仍需绑定相应版本。
5. 三方操作留痕与版本变化用于 Diff；事件订阅是链路的重要组成部分，需要检查事件接收之后如何真正触发宿主中的工作。
6. 完整目标覆盖首次接入、搜索回填、匹配写稿、本人审批、执行回读、事件/Diff、Memory Dream 和下一周期消费。
7. 不写、漏写、漏处理以及失败不交代，要在 `AGENTS.md` 和实际定时/事件任务正文中明确结果责任；代码承担可验证的校验、写入和结果核验。
8. 目标是其他人接入后，也能由其对应宿主 Agent 按 Skill 自主推进已授权工作；登录、本人决定和宿主真实能力仍是实际边界。

下面的问题用于补齐尚未确定的范围与事实，不重新讨论上述目标是否成立。

## 二、需要业务负责人明确的阶段目标

### B1：第一阶段验收哪一条完整业务闭环？

完整目标已明确。需要确定阶段交付顺序：第一阶段先验收哪一条从输入到实际结果的闭环？例如“搜索完成后自动交给推理侧并回填待审材料”“本人批准后执行并回写”或“本人改稿形成 Diff 并影响下一轮”。其他目标分别安排在哪一阶段？

请说明第一阶段的起点、最终可见结果，以及哪些后续能力可以明确留到下一阶段。不要仅用“接通事件”“增加接口”作为业务完成标准。

### B2：“任何一个人接入”第一批要覆盖哪些宿主组合？

需要区分当前本人环境的修复与可供其他人安装的交付。第一批明确支持哪些宿主、各宿主承担哪些角色？推理和执行是否需要同时支持由同一宿主承担，以及由两个宿主协同承担？

这里确认的是验收覆盖范围；实际工具能力由实现方探测，不能让本人凭产品介绍猜测宿主具备哪些接口。

### B3：新接入者最终应拿到什么？

请明确交付形态：可安装的 Skill 包、宿主接入说明、共享业务环境初始化方式、事件订阅组件、可调用写入代码分别需要提供到什么程度？需要由本人完成的账号授权和开放平台配置，应在首次接入的哪个步骤出现？

这不要求现在选择具体 SDK 或部署技术，先说明“用户安装后可以完成什么、需要手动做什么”。

### B4：事件触发与周期任务的业务预期是什么？

请明确哪些工作要求事件到达后主动触发，哪些可以等下一轮已配置任务处理。例如本人批准、本人改稿、搜索轮次完成、执行失败、Memory Dream，它们各自的业务优先级是什么？

现有频率、窗口与预算已经确认的直接复用。此处只确定工作如何衔接，不重新征询已登记数值，也不把所有事件默认解释成即时执行。

### B5：如何认定“三方协同已经可用”？

请确定第一阶段真实验收要覆盖的典型场景及通过标准：从哪一方发起、另一方在哪里收到工作、本人在哪里决定、最终在哪里看到结果？新接入验收是否需要在不同宿主上重复完成？

真实招聘发送不因验收而自动获准；可以先验证不会外发的闭环，再使用本人实际逐项批准的业务验证发送路径。

## 三、先由代码与既有 Schema 回答的问题

以下由 Codex/实现维护者读取代码、字段 Schema 和已保存协议后填写。只有发现具体冲突，才向业务负责人提问；不能把代码检查工作变成本人重新定义业务。

| 编号 | 必须检查的问题 | 应提供的结果 |
|---|---|---|
| C1 | `处理进度 × 批准状态` 的组合如何对应动作、等待与终态？共享字段与代码类型如何映射？ | 来源版本、联合转换表、具体代码入口；无法映射的组合单列 |
| C2 | 当前执行器从哪里读取本人批准及对应材料版本？是否额外依赖内部 ask/approval？ | 实际调用链；表内已批但内部无记录时的真实行为 |
| C3 | 飞书当前值、版本历史、原始事件与本地缓存分别保存什么？ | 数据权威与流转图；指出所有能独立改写业务当前态的位置 |
| C4 | 写入层现有代码能执行哪些原子操作？宿主从 CLI/MCP/其他工具如何调用？ | 真实入口、输入输出、错误结果、调用示例与测试证据；不存在的接口标待实现 |
| C5 | 各动作如何核对材料变化、重复执行、并发写入及未知发送结果？ | 对应代码与测试；版本冲突后的实际行为，不假定外部 API 提供原子比较写入 |
| C6 | Skill 入口如何按事件/任务/阶段渐进加载三方职责及写入协议？ | 当前路由、实际引用文件、缺失路由；无需一次加载全部 references |
| C7 | `AGENTS.md` 和宿主任务正文是否明确每项产物、回写、失败交代及恢复？ | 实际条款和任务正文回读；仅仓库文档修改的标“尚未部署” |
| C8 | 现有报告证明的是代码检查、本地记录完成，还是共享业务结果完成？ | 分开列出证明范围；遗漏项、待回写项是否会被掩盖 |

## 四、需要现有宿主/部署维护者回答的实现事实

### H1：现在实际运行的版本与链路在哪里？

- GPT、Muse、Codex 各自实际使用哪个 Skill/代码版本？是否读取同一份协议？
- 正在运行的任务、宿主提示词和适配器代码分别从哪里加载？哪些可以只读核验？
- 仓库内的本地 Worker/Pipeline 是否真的在这条线上调用？若未调用，当前由什么工具完成读取、执行与回写？

回答应提供可访问的代码位置、脱敏配置引用或真实任务回执。不需要提供凭证、个人材料正文或全量运行日志。

### H2：飞书事件订阅现在到了哪一步？

简报提出 Bitable 记录变更事件与长连接方案；这不证明当前账号已经配置或运行。请逐项核实：

1. 是否已有订阅应用、实际 event key、事件权限与接收组件？
2. 接收组件运行在哪里，由谁启动与恢复？是否已有可核验的新事件？
3. 实际 payload 是否包含稳定事件 ID、操作者、记录/字段、发生时间及 before/after？哪些信息必须再读取历史或当前记录补齐？
4. 是否已处理重复、乱序、断连、重启及接收成功但后续处理失败？
5. 当前 CLI 与 SDK 分别能完成什么？简报所述能力限制和版本条件是否与已安装版本一致？

请提供脱敏事件 fixture、版本、代码与接收回执；不要先按假设安装另一套接收服务。

### H3：收到事件之后，谁真正唤醒宿主 Agent？

这是当前尚未核清的关键实现问题：

- 接收事件的进程通过什么真实接口把工作交给推理或执行宿主？
- 宿主是否支持被主动触发，还是只能在已配置任务启动时领取？
- 触发后如何确定加载哪个 Skill 上下文、哪个岗位和哪个来源版本？
- 两个宿主如何认领、交接及避免重复执行？
- 是否已有从事件接收一直到宿主开始处理的真实回执？若只有事件落盘，应明确标为“接收已实现，宿主触发未核验”。

不能把发出通知、写入队列或 SDK 收到回调直接记为 Agent 已经开始工作。

### H4：搜索完成如何交给推理侧？

- `search_run_id` 与 `search_run_completed` 当前是否已存在于实际共享环境或运行协议中？
- 谁写完成回执，如何判断本轮入库范围及未完成项？推理侧通过什么方式领取？
- 若当前按每条岗位触发，是否会在 JD/材料尚未写完时抢跑？已有何种处理？

请提供实际字段/记录协议及一轮交接证据。缺少新字段时先记录缺口，不自行创建或把字段名提案写成现状。

### H5：批准、执行与回写现在如何运转？

- 本人在表内批准后，当前哪个任务会消费？它联合读取了哪些字段和版本？
- 动作成功、失败、结果不明分别写到哪里？回写失败由谁发现和恢复？
- 是否存在表内已批准，但内部条件导致不执行且不报告的实际案例？需要对应记录范围及可核验来源，不能只凭状态组合推断。
- 是否已有“动作已发生、回写未完成”的处理路径？如何确保恢复只补核验/回写，不重复外发？

不要求本人重复批准已明确批准过的同一阶段、同一材料。

### H6：Diff 和 Memory 现在实际接通到哪里？

- 当前 Diff 来自飞书原生事件/历史，还是宿主手工提交的原稿与改稿？
- 是否可靠区分本人、GPT、Muse、Codex 与未知操作者？实际以什么身份发起写入？若 AI 使用用户凭据，如何区分 AI 代操作与本人亲自决定？
- Search/Greeting/CV 各自有无实际消费者？Dream 是否真的调用推理，失败是否保留游标？
- 是否有一条完整证据链：本人变更 → 原始事件 → Diff → 记忆版本 → 下一轮实际输入 → 产物？

已有招呼偏好服务和合成测试应复用；这与真实飞书事件已进入学习链路分别核验。

### H7：实际定时/事件任务的结果约定是什么？

请读取当前任务正文，核对输入范围、三方职责、触发方式、每项产物、回写位置、回读验收、未完成交代与恢复。分别说明：仓库已有规范、宿主任务已加载、真实运行已验证。

当前任务读不到时记录“未取得/未核验”；本人报告已配置的设置不重新询问，不新建替代任务，也不擅自调整频率。

## 五、实现程度应如何填写

同一能力分别记录以下维度，不用一个“已完成”覆盖所有层面：

| 维度 | 需要回答什么 |
|---|---|
| 业务目标 | 要达成的可见结果、参与者及完成条件 |
| Skill 协议 | 是否有渐进路由、三方职责和阶段交接说明 |
| 可调用代码 | 是否存在真实入口、类型契约、错误处理和测试 |
| 宿主接入 | 当前宿主是否能调用，触发与授权是否可用 |
| 部署运行 | 是否实际配置了任务/订阅，并运行在明确版本上 |
| 业务验收 | 是否有来源、处理、回写及下一阶段消费的真实证据 |

建议以这张表汇总，逐行补证，不先把未知写成缺失：

| 能力 | 当前可确认的事实 | 尚需核实的实现程度 | 回答依据 |
|---|---|---|---|
| 渐进式 Skill 与三方协同 | 仓库已有渐进加载入口；本人明确要求覆盖完整协同链 | 当前已加载路由是否完整覆盖共享事件链 | C6、H1、实际 Skill 版本 |
| 飞书共享业务环境 | 已只读看到岗位/材料/记录结构与联合状态字段 | 各宿主是否一致消费，同步及写入链如何实现 | C1–C4、H1、H5 |
| 事件接收 | 简报给出订阅目标与方案 | 真实应用、接收组件、权限、payload 与恢复 | H2 |
| 事件触发宿主 | 尚未取得真实触发回执 | 触发接口、认领、渐进加载和执行是否接通 | H3 |
| 搜索到评估交接 | 仓库已有搜索/策略服务；简报要求轮次完成后领取 | 当前共享轮次协议与批量交接是否运行 | H4 |
| 本人批准到执行 | 业务语义已明确；所查本地路径仍依赖本地批准 | 当前真实宿主使用哪条路径，是否存在漏消费 | C2、H5 |
| 共享写入闭环 | 已知本地回执不直接证明飞书回写 | 实际写入工具、业务校验、回读与故障恢复 | C4、C5、C8、H5 |
| Diff / Dream / 下一轮消费 | 现有部分偏好服务和合成测试可复用 | 飞书输入及 Search/Greeting/CV 真实消费程度 | H6 |
| 定时与结果责任 | 已修订仓库规范 | 运行中任务是否加载，是否完成真实验收 | C7、H7 |

此前本地代码专项测试通过，只证明相应本地契约；默认路径全套基线仍有已记录失败。上述真实宿主链路不因本地测试通过而升级为已接通。

## 六、回答与后续收敛方式

回答按问题编号即可；可引用已有来源，不必重新抄录材料。每项说明“当前情况 / 依据 / 剩余缺口”，无法核实的明确写未核验。业务负责人回答 B 类；Codex/实现维护者先检查 C 类；现有宿主或部署维护者提供 H 类事实，避免所有问题都转交本人。

收齐关键答案后，才能确定第一阶段的端到端验收、可复用组件、真正缺失的代码与宿主接线，并修订此前的[实施任务单](workflow-memory-implementation-plan-2026-11-19.md)。此前任务单与文档修改保留为待复核草案，不作为已经确认的完整实现设计，也不代表现有运行任务已经更新。
