# GM 个人事实发现

GM 在首次接入、写作前发现关键事实缺口、收到本人更正或发现资料矛盾时使用本页。EM 只读材料。事实主档和技能栈沿用同一 Base 的 `材料` 表。

## 1. 先定位记录并读取本人已提供的资料

1. 用现有私有 `材料ID` 或已确认的材料记录绑定查询同一 Base。只把能确认归属本人的记录交给本流程。按需读取实际字段并完成分页，确认无记录和读取失败分别处理。
2. 读取本人已提供并授权访问、与当前任务有关的材料，包括 PDF、Word、项目材料、纯文本、本人答复和已有 Markdown。飞书附件用官方 `base +record-download-attachment` 按真实记录及文件标识读取，PDF 逐页提取，Word 读取段落和表格。扫描件用可用的 OCR 或视觉阅读核对。保存页码、章节、段落或本人答复作为可追溯来源。遇到权限或解析问题时标记不可读，保留原文件并继续使用其他来源。
3. 提取履历、经历起止时间、项目背景与目标、本人分工与决策范围、关键行为、方法、协作、交付物和成果。量化结果同时保留口径、范围、时间及归属。工具使用、产品方法、AI/Agent 和行业技能也可进入技能栈。按来源区分使用过、参与设计、独立交付和底层研发；材料只出现工具名称时保留待核实。
4. 四类资料分开标明：本人已确认（明确答复或材料内有可追溯的本人确认）；材料明确记载（保留出处和原意）；GM 归纳的能力（保留归纳依据）；待核实或有矛盾（保留差异和缺口）。原作者陈述与 GM 的推断分别记录。角色选择、提问里的候选答案和风格偏好都不构成事实确认。

## 2. 在原记录上增量维护

| 可用资料 | GM 工作 |
|---|---|
| 事实主档和技能栈都在 | 读两份独立材料，查一致性和本次变化，按需更新 |
| 只有事实主档 | 从可追溯的事实派生独立技能栈，保留原有确认状态 |
| 只有技能栈 | 核对技能出处，从其他资料或访谈建立事实主档，缺少经历来源时不从技能名补造项目 |
| 只有简历 | 解析 PDF 或 Word，依据原文生成事实主档和技能栈初稿 |
| 只有零散材料 | 汇总可定位的事实，记录来源、冲突和覆盖缺口 |
| 暂无可用资料 | 从一段相关工作或项目经历开始访谈，有可用事实后再建资产 |

保留 `简历模板`、`技能栈`、`事实整理` 三列。已授权的原始简历可直接作为输入。沿用已有简历模板，补齐缺失的事实主档和技能栈，无须让用户先制作这两份 Markdown。

更新使用现有材料记录及其真实字段。已发现的主档沿用原有 `材料ID`。确实没有主档时，可用单人 Base 中约定的 `CareerHarness:personal-facts` 作为稳定 `材料ID`，精确查重后创建。官方 `+record-upsert` 只有提供真实 `--record-id` 才更新，无记录 ID 会创建。多宿主同时维护时先协调该 `材料ID` 的写入者。派发前私有记录 `creation_pending=true`，写后按 `材料ID` 读回并绑定真实记录。结果不明时续查原记录。已有多条可信主档、旧绑定不可访问或归属不明时，先解决定位。

用授权的附件工具写回对应列。官方 `base +record-upload-attachment` 以真实 `--record-id`、`--field-id` 和私有文件路径追加附件。写前比较已读内容，相同跳过。新版本读回核实后，在同一材料记录沿用已确认的有效版本；未读或归属不明的旧附件保留。更新以新增的事实和已核实的修正为限，保存为 Markdown。材料写回用注册 Bot，读回字段和内容。岗位材料写作、模型临时文件和真实引用都留在本人私有区。

## 3. 按当前任务检查事实是否足够

先判断目标岗位或当前任务需要支撑哪些关键能力主张，再逐项对照本人职责、行动和成果。用八个维度找关键缺口：背景（Context）、职责（Ownership）、行动（Action）、方法（Method）、协作（Collaboration）、交付（Deliverable）、影响（Impact）、来源与确认状态（Attribution）。任务有已知 JD 时优先使用其中真正影响判断的要求。八个维度是检查视角，资产无需逐项填满。

- `sufficient`：现有材料足以支撑当前任务的关键主张，直接继续。
- `needs_clarification`：仍有关键缺口。一次优先问一个问题，说明已经从哪段材料读到了什么，只问尚缺的责任边界、关键行动、决策或成果归因。
- `proceed_with_gaps`：用户跳过时保留具体缺口，继续能由现有事实支撑的工作。没有相关来源的主张省略，无法可靠评级时说明信息不足，EM 的独立检索和入库照常按其条件判断。

收到答复后将答复本身作为来源，修订具体主张的确认状态，再判断是否需要下一题。比如材料写到参与一种上线方案时，只问「具体是由您决定上线范围，还是您负责执行已确定的范围？」按本人实际回答记录。无需逐条批准 Markdown。

## 4. 在正常任务中调用

1. GM 用 `jobagent setup personal-facts --request <私有请求>` 求出下一步。输入 `materials_complete`、匹配的 `records=[{record_id,has_facts,has_skills}]`、已有 `bound_record_id`、上次是否有待核查的创建 `creation_pending`，以及 `sources=[{ref,kind,status,confirmed_by_user}]`。来源类型为 `pdf`、`word`、`project`、`text`、`interview`、`facts`、`skills`，状态为 `pending`、`read`、`unavailable`。已有附件也须列入来源并标记读取范围，同一资料的不同页或段落可分别登记。只有该段来源明确包含本人对具体主张的确认时，才标记 `confirmed_by_user=true`。工具输出计划，GM 执行材料读取、事实提取、追问和写回。
2. `inspect_materials`、`resolve_material_record` 和 `read_sources` 表示先完成定位和读取。`record_action=create_if_absent` 表示内容可写入时先查重；`reuse` 使用返回的现有记录。按 `facts_action` 和 `skills_action` 核对、起草或保留附件。
3. 按重要性排列 **本任务的必要主张** 后传 `assessed=true` 与 `claims=[{claim,status,source_refs,question,skipped}]`。状态取 `confirmed`、`documented`、`inferred`、`unverified` 或 `conflicting`。只把真实读到的来源写入 `source_refs`。把针对该主张的具体问题放入 `question`；用户跳过质询则为该项置 `skipped=true`，跳过当前任务余下访谈使用 `skip_interview=true`。按返回的 `usable_claims` 和 `gaps` 继续。Shell 工具不可用时按同一决策顺序执行。
4. 新 JD、本人补充或更正、简历指标缺少口径，或已核实的本人反馈指出事实错误时，在当次工作中重新评估相关主张。有更新就改原主档，技能状态受影响时同步技能栈。未解决的矛盾或未确认事实继续保留对应状态。
