# Initial Setup：先建一份可用的飞书 Base，再运行 Skill

**用户先拥有业务表，Agent 后接入业务表。** 第一次接入的首要交互不是评级、发招呼或询问个人资料，而是请用户在飞书自行建好一份包含所需 Schema 的 Base。完整清单见 [飞书 Base 最低 Schema](feishu-schema-bootstrap.md)。同一个 Base 内是五张工作表，而不是五个独立 Base。

**轻量原则：** 已建且已核验的 Base 直接复用；不重复建表、不要求用户反复交资料。只查实表与差异，不为完成 setup 复制另一套状态。

## 0. 恢复已有设置（避免重复初始化）

先读取私有 `settings.json`、已绑定的 Base 坐标和角色；若同一 Base 的必需字段已经验收、当前业务 Skill 依赖仍齐全，直接恢复对应角色并运行，不重新要求创建。配置找不到、Base 不可访问或必需字段缺失时，才进入下面的建表关卡。

## 1. 请用户先在飞书建立 Base

如果用户尚无可用 Base：

1. 告诉用户先在飞书**自行新建一份多维表格**，在其内部按 [最低 Schema](feishu-schema-bootstrap.md) 配置 `岗位`、`材料`、`Human Signals`、`搜索与匹配记忆`、`招呼语表达记忆` 五张表，并设置允许本人的 Bot 访问。
2. 不预先展开岗位检索配置、简历写作或其他业务 Skill，不替用户建一份未经确认的 Base。
3. 只要求用户建完后给出 Base 链接；不要索取 token、appSecret。若用户已有 Base，优先复用，不要求重建。
4. 没有拿到可访问的 Base 与足够的 Schema 之前，停在 Setup；此时不能宣布“CareerHarness 已就绪”。

## 2. 连接、只读核查并准确列差异

1. 检查飞书 CLI/桥接可用性与授权（Windows `lark-cli.cmd auth status --json --verify`）；复用用户现有登录，不无故要求重登。钉钉 CLI 的业务表读写未验收，不假设兼容。
2. 通过官方 CLI/MCP 读取用户 Base 的表名、字段名、字段类型、单选选项、Workflow；把语义域映射到用户真实表，写到**私有**配置，不在仓库固化 ID。
3. 列出“实际存在 / 缺失 / 类型不符 / 单选值不符 / 无访问权限”，并标明哪些阻塞运行、哪些是可选扩展；**不得把 Bot 返回的未知编辑权限推断为有权限**。
4. 新用户由本人根据差异完成建表/修表；已存在的内容不得覆盖。Agent 未经具体授权不创建表/字段、启用 Workflow 或更改权限。
5. 读取同一 Base 的一条合成记录或已有记录的映射视图进行只读核查；需要真实写回测试时必须取得本人的具体授权。
6. `岗位` 的 `Muse处理` 与 `GPT处理` 必须保留双向通信约定；`材料` 应识别真实的 `简历模板`、`技能栈`、`事实整理` 三个附件字段，不再要求旧版 `附件` / `准确全文` 字段。

## 3. 验收 Human Signals 与 Memory 链路

- 核对监听 `批准状态`、`处理进度`、`招呼语`、`匹配档位` 的四条 Workflow，写入目标必须是同 Base 的 `Human Signals`；开关状态需如实报告。
- GM / EM 共用一个注册 Bot 写入身份；Dream 只分析经真实记录修改历史可判定为本人操作的 Signal。Bot 操作与操作者未知均不得直接提升为本人偏好。
- 搜索与匹配记忆、招呼语表达记忆各保留一条当前有效版本；没有记录时可保持空白，不虚构历史学习结果。
- Base 只读验收、字段写入验收、Workflow 触发验收、Dream 实际运行验收要分别报告；前者完成不能冒充后者完成。

## 4. 填充材料表（Schema 验收之后）

1. 如果 `材料` 中已经保存简历、技能栈和个人事实资料，按需直接读取，不让用户重新上传。
2. 缺少时才向用户收集简历 PDF、技能栈 Markdown 和个人事实 Markdown：`简历模板` 存 PDF，`技能栈` 存独立技能文档，`事实整理` 存个人事实文档；`材料ID` / `岗位类型` 用于定位和管理。
3. 用户选择对话补充事实时，一次只聊一小段，先确认理解再追问职责、推进过程和可验证结果；用户可跳过。
4. 资料由有写入权的 GM/Setup 角色整理，EM 只读，不能把技能栈变成评分状态机；不要求用户审核整份事实 Markdown。

## 5. 绑定角色与私有求职设置

一条消息处理一个需要用户决定的事项，已在现有配置里有答案就不重问。

1. 确认当前宿主承担 GM、EM，还是两者兼任。分立宿主时从私有配置恢复本机 MCP bridge / Tunnel，**只在 Bootstrap 建立或复用**，不按每个 Skill 重建。
2. 求职方向、年限、城市与远程条件、薪资底线及口径、硬筛与排除词。
3. 招聘平台（BOSS、猎聘、智联、LinkedIn 等），**每个平台**使用 Chrome 插件、云浏览器或 MCP；尚未验证的执行途径先只读验收。
4. 寻源运行日程、每平台与总配额、简历母版及允许改写范围。
5. 状态收束：是否启用超时、时长、自然日/工作日、起算点、超时目标状态及需暂停的情形；不得把某一用户的 48 小时约定写成所有用户默认值。被动超时与本人主动终止需在历史上区分。
6. 招聘方明确拒绝后是否授权 EM 直接转为 `已终止`；没明确授权就交 GM/本人处理。

结果只写私有 `settings.json`，不写公开仓库。

## 6. 业务 Skill 解锁与首次运行

仅在 **Base 可以访问、核心字段完整、字段与角色映射有效、材料已就位、所需私有业务设置已确认** 后：

1. 先读取真实 `批准状态`、`处理进度`、交接字段，按职责装载 `roles/GM.md` 或 `roles/EM.md`。
2. GM 可以读 JD、匹配、生成初稿；EM 可以按已批准的项目运行搜索和受权操作。**不因为 Base 就绪自动发送招聘消息，也不代填 `已批准` / `已拒绝`**。
3. Dream 只在四条 Signal Workflow 与操作者核验通过后由原有宿主调度；10 工作日异常干预与被动超时补查须各自完成实际调度验收，否则标记“契约就绪，运行未验收”。
4. 首轮报告清楚区分已能读取、已能写回、Workflow 已触发、业务 Skill 已执行。缺哪一层只报告那一层，不装作全链已经上线。

## 7. 完成后的简短交付

只需告诉用户：当前 Base Schema 是否通过、材料与 Memory 是否可消费、GM/EM 部署及平台方式、哪些 Skill 可以开始、尚未通过的权限/Workflow/运行验收。不重复要求用户填写先前已确认的材料或设置。
