# 轻量 Skill 化架构：决定、实表映射与待定事项

> 本文保留 2026-11-21 的设计和验收记录。当前角色顺序、材料建设与本人归因请以 [Initial Setup](../../skills/job-hunting/references/first-use.md)、[个人事实发现](../../skills/job-hunting/references/personal-fact-discovery.md) 和 [本人 Trace 契约](../../skills/job-hunting/references/human-signal-capture.md) 为准。

**日期：** 2026-11-21　**基线：** PR #36 头部 `f3eb022`（本分支 `claude/lightweight-skill-refactor` 由它切出，未改动 PR #36 远端分支）

本文记录本人已明确的架构方向、对本人 Base 的只读核对结果，以及开始删改代码前仍需本人裁定的事项。它是方案与差距记录，不证明任何能力已落地；能力状态仍以[能力目录](../../skills/job-hunting/references/capability-catalog.md)为准。文中不含任何 Base、表、字段或 Workflow 标识及业务记录内容。

## 1. 本人已确认的方向（2026-11-21）

**总原则：能轻度设计就轻度设计。** 不另起炉灶写代码，不加防御性校验层，出错就让它报错（let it crash）；能复用现有实现、`lark-cli` 与多维表格自身能力的就复用，不造新轮子。规则优先写进角色 md 与 Skill reference。

- **轻量化。** 仓库以 Skill 为主体，按需调用、渐进加载。保留招呼语、简历等写作类 Skill；旧的浏览器操作壳、自研 worker 与本地状态体系不再是产品路径。
- **三方协作 loop：**
  - **Generative Model（GM）**：GPT / Claude。读取 Bitable 中回传的 JD 与材料页信息，产出定向内容（招呼语、简历等）并写回多维表格。
  - **Executive Model（EM）**：Muse / Grok bot / WorkBuddy 等桌面界面 Agent。负责岗位检索、获取、填入基本信息和执行已批准动作；不做定向生成，是 GM 产物的消费者。
  - **Human**：对 GM 产物筛选、修改、评价并作最终批准；操作轨迹由多维表格统一记录为 Signal。
- **Bitable 是全局唯一状态机。** 由 `lark-cli` 驱动；宿主（EM 层的 Personal Agent）载入本仓库 Skill，经 Initial Setup 完成初始载入并生成看板。它取代各 Agent 内部 worker 与 SQLite，同时是 GM、EM 产物的载体和复用消费的表单。
- **Memory。** GM 在本地时区凌晨消费多维表格中的 trace，做归因、聚类与多重分析，形成 Search / Greeting Memory；EM 在下一轮搜索前消费 Search Memory，GM 在下一轮写招呼语、简历前读取 Greeting Memory 作为 guideline。
- **基线。** 在 PR #36 的代码与契约上继续，不另起 main 分支方案。

### 1.1 角色部署、写入身份与字段归属（本人补充，2026-11-21）

- **Initial Setup 先问角色。** 首先询问当前环境充当 GM、EM，还是两者兼任。任何用户都可以让 GM 与 EM 由同一宿主承担，只要本人允许；两者都通过多维表格与本人交互。
- **分立部署时建立本机 MCP 桥梁。** GM 与 EM 由不同宿主承担时，经本机 MCP bridge（Tunnel）连接。桥梁脚本路径与 Tunnel ID 属于本人私有配置，不写入公共仓库；Tunnel 在 Skill Bootstrap 建立或复用，不在每个任务重建。
- **GM 与 EM 各有自己的角色 md。** 角色 md 写明各自可写字段、读取范围与禁止事项，按角色加载，不靠代码区分“哪个 Agent”。
- **Initial Setup 先收集个人资料。** 先取得本人的简历、技术栈、事实库等个人信息，写入“材料”表；Base 的主 Schema 完整保留，日后按不同用户的实际需要扩展。
- **写入责任。** 首次 setup 的写入由第一个开始 setup 的 Agent 负责；此后 GM 负责更新，EM 负责消费与执行。
- **单一 Bot 写入身份。** GM 与 EM 的所有写入都通过同一条 CLI、以同一个飞书 Bot 身份进行，不再区分 Bot 之间的差别。由此，**记录历史中非该 Bot 的操作即人类操作**；Trace 与 Signal 只采集人类操作，Bot 写入一律不进入 Dream。
- **关键字段只归 GM。** EM 的角色 md 中不负责 `匹配档位`、`匹配理由`、招呼语草稿（`招呼语`）与简历（`简历cv（PDF）`）的写入；这几个字段的改写一定来自 GM 或本人。

字段归属如下（已经本人在第 5 节确认）：

| 字段 | GM | EM | 本人 |
|---|---|---|---|
| `匹配档位`、`匹配理由`、`招呼语`、`简历cv（PDF）` | 写 | 只读 | 修改即 Signal |
| `岗位名`、`公司`、`薪资原文`、`原岗位链接`、`JD全文`、`招聘平台`、`岗位ID` | 只读 | 写（检索、获取、填入基本信息） | 可改 |
| `处理进度` | 只读 | 写执行结果 | 可改，修改即 Signal |
| `批准状态` | 评级后写 `待你批准`（唯一可写值） | 只读，执行前读取最新值 | **仅本人**填 `已批准` / `已拒绝`；更新即 Signal |
| 材料表 `你的决定` / `你的原话` | 只读 | 只读 | **仅本人** |
| `Muse处理`（GM 给 EM 的回复与搜索策略要点） | 写 | 下一轮非空即读取并处理，处理后可修订 | 可直接修订 |
| `GPT处理`（EM 执行中的反馈） | 下一轮非空即读取并处理，处理后可修订 | 写 | 可直接修订 |
| 材料表个人资料（一份简历 + 一份 md） | 首次 setup 写入，之后由 GM 在 md 内增删改 | 只读 | 可直接修订 |

## 3. 代码层与业务的差距

1. **GM ↔ EM 的实际通信字段没有建模。** `GPT处理` 与 `Muse处理` 是两侧互相留言、交接搜索策略要点的列；PR #36 代码未引用它们，也未引用 `JD全文`、`简历cv（PDF）`、`待你处理（Memo）`。代码只用到 `处理进度`、`批准状态`、`招呼语`、`匹配档位` 等少数字段。
2. **“材料”表为空，个人资料尚未入表。** 已确认的个人事实目前只在本地 SQLite（Candidate Evidence）。按 1.1 由 Initial Setup 把简历、技术栈、事实库写入“材料”表；按第 5 节定案，个人资料整理为一份 md 文档放进材料表现有字段，不新增字段；若需给 `类型` 增加选项来区分个人资料与待批材料，仍属 Schema 变更，须先展示准确差异并经本人确认。
3. **以本人身份写入会污染归因（已由 1.1 定案解决）。** 以 `identity=user` 写表时，记录历史中的 open_id 与本人相同，无法区分本人与 Agent；实表中已出现操作者显示为“……的飞书 CLI”的 Signal（已按协议标为 unknown）。定案后 GM / EM 统一用一个 Bot 身份写入，非 Bot 操作即人类操作。`FeishuConfig.identity` 随之改为 Bot；Human Signals 中 Bot 写入的行由 Dream 第一步按规则排除，不另写代码。
4. **审批与字段归属不靠 Base 权限强制（已由第 5 节定案）。** 本人决定不启用高级权限；GM / EM 的隔离由角色 md 与复用 PR #36 `feishu patch` 的写前字段白名单承担，白名单同时阻止 Agent 写入 `已批准` / `已拒绝`。
5. **重型代码与新路径无关。** PR #36 约 5.4 万行 Python 中，SQLite 存储约 1.33 万行（39 个迁移、123 张表），CLI 约 0.78 万行，bridge / MCP 约 0.56 万行，岗位流水线约 0.42 万行，浏览器连接器约 0.18 万行，Console 约 0.15 万行，另有 53 个前端文件。在新 loop 中检索与执行由 EM 宿主完成、表访问由 `lark-cli` 承担，这些模块大多没有生产消费者。

## 5. 本人裁定（2026-11-21）

0. **前置依赖。** 本人的多维表格环境必须已安装飞书或钉钉 CLI 并完成授权，否则无法开始。Initial Setup 第一步检查 CLI 是否存在、授权是否有效，不满足即停止并告知本人如何安装与授权，不以其他方式绕过。当前只验证过飞书 `lark-cli`；钉钉 CLI 的表格读写能力尚未核验。
1. **投递审批（D1，已定）。** 只有本人能在 `批准状态` 上填 `已批准` 或 `已拒绝`，已批准是最高权限。本人修订好材料并填入后，Agent 读取到即视为批准，不要求回到对话重复批准；这次状态更新同时是一条人类 Signal。
   - GM 每看完一份 JD 完成评级后，把 `批准状态` 写为 `待你批准`；这是 GM 唯一可写入该字段的值。
   - EM 执行前读取 `批准状态` 与材料的最新值，按最新值执行，不另设版本绑定机制。
   - 批准本身不等于写作偏好，由 Dream 判断去向。
   - 现有三条 Workflow 监听 `匹配档位`、`招呼语`、`处理进度`，不含 `批准状态`；要把批准记为 Signal，需新增或调整一条 Workflow，属于 Base 变更，须本人确认。
2. **材料表承载个人资料（D2，已定）。** 材料表保存本人在 Initial Setup 时上传、或在问答中提及的全部个人资料（即仓库中目前称为 Evidence 的内容）。只保留**一份简历**与**一份 md**：md 由 Agent 自由组织以覆盖全部内容，此后只在 md 内增删改，用时读取；不新增字段。md 建议放在 `准确全文`（文本字段的记录历史可显示前后差异），简历放 `附件`。
3. **确定性校验层（D3，已定）。** 只保留两项代码检查，见第 6 节。
4. **不启用高级权限（D4，已定）。** 只做好 GM 与 EM 的权限隔离（角色 md + 写前字段白名单）；GM 与 EM 为同一宿主时，两角之间无需隔离。
5. **交接列（D5，已定）。** 两列可互相修订。`Muse处理` 由 GM 写入，EM 下一轮执行时若不为空即读取并处理；`GPT处理` 由 EM 写入，GM 下一轮同理。需要本人意见时，在 Agent 交互层直接提及本人并取得意见，或由本人直接修订相关内容；不另建通知字段。处理完成后接收方修订该列（清空或注明已处理），避免下一轮重复处理。
6. **EM 执行方式与寻源设置（已定）。** EM 可选三种执行方式，按平台在开始时选定：
   - 云端浏览器：可做定时任务，但封号率高；
   - MCP：猎聘、领英；
   - 浏览器插件：随时可用，稳定安全。

   多久搜一次、每个平台搜多少，都在开始时定好并写入私有 `settings.json`；之后各轮只读取，不重复询问。任何方式都不绕过登录、验证码、风控或限流。
7. **废止 Evidence 概念（已定方向，措辞待 P1 确认）。** 仓库中的 Evidence 模型与术语（`CandidateEvidenceService`、canonical Evidence、`evidence-policy.md` 等）退役，统一改称材料表中的个人资料 md。

## 6. 确定性校验层（D3 结果）

本人逐项裁定后，代码只保留两项：

| 检查 | 保留理由 |
|---|---|
| 写前字段白名单：GM、EM 各自只能写归属字段；GM 对 `批准状态` 只能写 `待你批准`；任何 Agent 都不写 `已批准` / `已拒绝` 与 `你的决定` | 不启用高级权限后，GM / EM 隔离与“AI 不代批”的落点 |
| 简历 PDF 渲染与核对：从获批正文生成 PDF，回抽文本比对，确认无内部批注 | 附件内容必须与获批正文一致 |

不做的检查及本人理由：

| 检查 | 本人裁定 |
|---|---|
| 执行前门禁（`处理进度 × 批准状态`） | 不用，已批准权限最高 |
| 批准来源核验（记录历史判定非 Bot） | 不用，不存在这个风险；写前白名单已阻止 Agent 写批准值 |
| 材料版本绑定 | EM 执行前读取最新值，不额外设计 |
| Memory 发布校验 | 不套额外判断；若 Memory 上线后批准通过率仍然很低，则回头重新检查 Memory |
| 禁用表达检查 | 不需要，本人会自己审阅所批准的内容 |
| 主张覆盖检查 | 不需要，本人会自己审阅；批准状态不需要 Agent 越级判断 |
| Signal 归因与去重 | 待澄清：该项指 Human Signals 表的行，而非 Dream 写入的 md，见第 8 节 |

## 8. 待澄清

- **Signal 归因。** 三条 Workflow 在字段被任何人改动时都会向 Human Signals 追加一行，包括 Bot 的写入（实表中已有操作者为“……的飞书 CLI”的行）。“Trace 只取人类”需要有一步把 Bot 写入的行排除。建议不写代码，作为 Dream 的第一步规则：读取 Signal 时丢弃操作者为登记 Bot 的行，同一岗位的连续修改合并看待。
- **核心主张的措辞（已定，2026-11-21）。** GM 只用材料 md 写招呼语与简历、不编造；材料 md 与 Memory 由 GM 维护、直接发布，不要求本人审批长文档。事实不对、不清或越界时，本人在 `批准状态` 驳回或直接修改 `匹配档位`、`招呼语`、`处理进度`，被 trace 捕捉后由 GM 查证并写入 Memory。
