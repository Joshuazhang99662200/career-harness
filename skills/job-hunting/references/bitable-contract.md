# 多维表格契约：三方共用的一张表

GM、EM 与本人只通过本人的多维表格协作。它是唯一业务状态源，也是 GM、EM 产物的载体。本页是三方共用的最小约定；各自的做法见 [GM.md](../roles/GM.md) 与 [EM.md](../roles/EM.md)，CLI 读写与回读细节见 [共享飞书环境](feishu-shared-source.md)。

业务状态保留在 Base。GM 与 EM 首次启动均走 [Initial Setup](first-use.md)，由官方 CLI 发现、复用或创建工作区并验收。配置错误在对应关卡报告。

## 前置依赖

本人环境必须已安装飞书或钉钉 CLI 并完成授权。开始任何工作前先检查 CLI 是否存在、授权是否有效；不满足就停止，告诉本人如何安装与授权，不以其他方式绕过。目前只验证过飞书 `lark-cli`；钉钉 CLI 的表格读写尚未核验。

## 五个语义域

只按语义名引用，表名、表 ID 与字段 ID 都在 Initial Setup 时从本人 Base 实际读取，存进私有配置，不写进仓库。

| 语义域 | 作用 |
|---|---|
| 岗位 | 岗位信息、JD、匹配、招呼语、简历、处理进度、批准状态、交接留言 |
| 材料 | 简历模板、独立技能栈 Markdown、事实整理 Markdown（分别为附件列）。三份资料可按需补齐，GM 维护、EM 只读 |
| Human Signals | 经已登记本人身份筛选后写入的岗位修订轨迹 |
| 搜索与匹配记忆 | EM 下一轮搜索前读取 |
| 招呼语表达记忆 | GM 写招呼语、简历前读取 |

## 写入身份

GM 与 EM 的业务写入使用同一个已注册的 Bot。原生事件匹配本人的实际操作者身份后才可写 [Human Signals](human-signal-capture.md)，Bot 原填值用于对照。

## 字段归属

| 字段 | GM | EM | 本人 |
|---|---|---|---|
| 匹配档位、匹配理由、招呼语、简历cv（PDF） | 写 | 只读 | 可改，改动即信号 |
| 岗位名、公司、薪资原文、原岗位链接、JD全文、招聘平台、岗位ID | 只读 | 写 | 可改 |
| 处理进度 | 只读 | 写执行结果 | 可改，改动即信号 |
| 批准状态 | 评级后写 `待你批准`（唯一可写值） | 只读 | **只有本人**填 `已批准` / `已拒绝` |
| Muse处理 | 写 | 读 | 可直接修订 |
| GPT处理 | 读 | 写 | 可直接修订 |
| 材料表的简历模板、技能栈、事实整理 | 按 `材料ID` 读取或建设，在原记录增量更新 | 只读 | 可直接修订 |

写前字段白名单复用 [共享飞书环境](feishu-shared-source.md) 中 `jobagent feishu patch` 的角色白名单；GM 与 EM 由同一宿主承担时，两角之间不再隔离，但任何 Agent 都不写 `已批准`、`已拒绝`。

## 批准

- 只有本人能把 `批准状态` 填为 `已批准` 或 `已拒绝`。已批准是最高权限：本人修订好内容并填入后，Agent 读取到即视为批准，不要求回到对话再批一次。
- EM 执行前读取该岗位的最新值，按最新的招呼语、简历与批准状态执行。
- 批准状态的每次更新同时是一条本人信号；批准本身只说明本人同意这一份内容，不等于写作偏好，由 Dream 判断它的意义。

## 本人只做轻量操作

本人可直接修改 `批准状态`、`匹配档位`、`招呼语`、`处理进度`。原生事件接收已验收时，确认是本人操作后才写入 Human Signals。材料附件与两份 Memory 由 GM 维护。本人纠正的事实问题由 GM 查证并更新材料。

## 交接留言

- `Muse处理`：GM 写给 EM 的回复与搜索策略要点。EM 下一轮执行时若不为空，读取并处理。
- `GPT处理`：EM 写给 GM 的执行反馈。GM 下一轮若不为空，读取并处理。
- 处理完成后，接收方修订该列（清空或注明已处理），避免重复处理。
- **结构化任务（CH10D）。** 一条要跟踪的委托或回执用一行开头的任务键 `CH10D-<岗位ID>-<类型>-<日期>`，即 `request_id`。写之前先看两列里有没有同一个键，有就接着处理，不写第二份；写时追加，不覆盖别人的留言，写后读回。委托写在 `Muse处理`（GM → EM），回执写在 `GPT处理`（EM → GM），字段归属不变。任务写下了不等于已执行，有回执才算有结果。
- 需要本人意见时，在 Agent 与本人的对话里直接提及本人；或由本人直接修订表中内容。不另建通知字段。

## 私有设置

Initial Setup 时确定、之后各轮只读取的设置写进本人私有的 `settings.json`，不进仓库：

- 当前宿主承担的角色：GM、EM 或两者兼任；
- 本人选择的招聘平台、覆盖方式及禁用项，以及当前宿主的能力验收与路由，见 [招聘平台能力路由](platform-capability-routing.md)。
- 日程、每个平台每轮搜多少与合计上限、硬筛条件与排除词、超时收束规则、EM 的事先授权；
- 简历母版、默认改写模式与锁定区域；
- GM 与 EM 分立时所用的本机 MCP bridge（脚本位置与 Tunnel 标识）；
- Bot 身份、真实 Base 和表字段坐标，以及原生 Trace 接收宿主的身份绑定与验收记录。

已确认的设置直接复用，不重复询问；只有本人主动要求调整时才修改。任何执行方式都不绕过登录、验证码、风控或限流。
